#1Compare array-based vs list-based implementations of stacks and queues:
Memory layout
Array implementation stores elements in a single block of memory. Linked list implementation stores elements as separate nodes in memory, each pointed to by a pointer.

Resizing behavior
Arrays have a fixed capacity and sometimes need to be resized when they grow. Linked lists grow dynamically and never need to be resized.

Cache friendliness
Arrays are cache-friendly because elements are stored next to each other in memory. Linked lists are cache-unfriendly because each access involves a pointer to a different location in memory.

#2Why is std::vector a natural fit for a stack, but awkward for a queue?
A stack inserts and removes elements from the same end. std::vector supports efficient push_back and pop_back operations in constant time, so it models a stack naturally.
A queue removes elements from the front, and removing the first element of a vector requires shifting all remaining elements, which is linear time. Therefore, std::vector is inefficient for a queue.

#3Define the invariant for:
Stack invariant:
Only the most recently inserted element (the top) is accessible for removal.

Queue invariant:
Elements are removed in the same order they were inserted (first-in, first-out).

#2Why is overloading a compile-time convenience?
The compiler chooses which function to call based solely on the argument types before the program executes.

#3Why is overriding a runtime contract?
The function that executes depends on the actual object type at runtime through dynamic dispatch (virtual functions).

#4Why do beginners confuse the two?
Both use identical function names and appear syntactically similar.

#5Why is that dangerous?
A programmer may believe they replaced behavior when they actually created a different function, causing the program to compile but behave incorrectly.

#5 When is the copy constructor invoked?
The copy constructor runs when a new object is being created using an existing object as its initializer. The object does not exist yet, so C++ must build it from scratch, and the copy constructor defines how to build a new object from another.

#1When is the assignment operator invoked?
The assignment operator runs when both objects already exist and one is being overwritten. The target object already has a valid state/resources. Assignment must replace that state safely (often requiring cleanup first).

#2Why do both exist?
They solve two different problems:
Copy constructor: “How do I create a brand-new object as a copy?”
Assignment operator: “How do I replace the contents of an existing object?”
In particular, assignment must handle:
Self-assignment (a = a)
Cleaning up old resources before copying new ones
preserving invariants even if copying fails (exception safety)
That is why C++ cannot treat them as the same operation.

#3What subtle bugs appear if you confuse them?
If your class owns heap memory (or any resource), the default “memberwise copy” causes serious errors.

Example bug (shallow copy → double delete):

class Buffer {
    int* data;
    int n;
public:
    Buffer(int n) : data(new int[n]), n(n) {}
    ~Buffer() { delete[] data; }
};


If you copy without defining proper copy behavior:

Buffer a(10);
Buffer b = a;   // copy constructor does shallow copy (data pointer copied)


Now a.data and b.data point to the same array. When both destruct, you get double deletion.

Example bug specific to assignment (resource leak):
Buffer a(10);
Buffer b(20);
b = a; // if assignment doesn't delete b’s old data first → memory leak

#4Why this happens: Copy construction is about initializing, assignment is about replacing—replacement must clean up old resources and handle self-assignment.

#1Why C++ cannot overload ., ::, and sizeof
These operators are required by the compiler to determine type structure and object layout. Allowing them to be overloaded would make program compilation ambiguous and unreliable.

#2Why operator+ should not mutate the left operand
The + operator represents mathematical addition, which is expected to produce a new value without changing the original operands. Mutating the left operand violates user expectations and leads to unpredictable behavior.

#4Why operator<< is almost never a member function?
In the expression std::cout << object, the left operand is std::ostream. Since the class does not own std::ostream, the operator must be a non-member function.

Point2D Implementation

#include <iostream>

class Point2D {
private:
    int x;
    int y;

public:
    // default constructor
    Point2D() : x(0), y(0) {}

    // parameterized constructor
    Point2D(int x, int y) : x(x), y(y) {}

    // copy constructor
    Point2D(const Point2D& other) : x(other.x), y(other.y) {}

    // addition
    Point2D operator+(const Point2D& rhs) const {
        return Point2D(x + rhs.x, y + rhs.y);
    }

    // subtraction
    Point2D operator-(const Point2D& rhs) const {
        return Point2D(x - rhs.x, y - rhs.y);
    }

    // equality
    bool operator==(const Point2D& rhs) const {
        return x == rhs.x && y == rhs.y;
    }

    // inequality
    bool operator!=(const Point2D& rhs) const {
        return !(*this == rhs);
    }

    // friend output operator
    friend std::ostream& operator<<(std::ostream& os, const Point2D& p);
};

std::ostream& operator<<(std::ostream& os, const Point2D& p) {
    os << "(" << p.x << ", " << p.y << ")";
    return os;
}

Inheritance expresses identity (“is-a”).

Composition provides modularity, clearer ownership, and safer system evolution, because changes to one component do not automatically affect all derived types.
